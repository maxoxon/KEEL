# Установка KEEL

Инструкция для человека. **Делай в терминале, не через omp** - копирование файлов не требует
рассуждений, а модель на таких задачах зацикливается.

KEEL - это набор файлов поверх уже установленного omp: одно расширение (`keel.ts`), три слоя
инструкций (`AGENTS.md`, `APPEND_SYSTEM.md`, `RULES.md`), пять агентов, `config.yml` и `models.yml`.
Он не форкает omp и не трогает твои логины - только кладёт файлы в конфиг-директорию.

---

## 0. Что тебе понадобится

- Установленный `omp` (сам бинарь ставится отдельно, не входит в этот архив).
- Доступ хотя бы к одному провайдеру моделей. Проще всего OpenRouter - один ключ, много моделей.

## 1. Аутентификация (креды НЕ в config.yml - их не затрёт установка)

omp хранит ключи и логины в своей базе (`agent.db`), отдельно от `config.yml`. Поэтому копирование
файлов харнесса **не трогает твои креды**. Есть два пути, выбери любой:

**a) Через логин (интерактивно, кладётся в agent.db):**
```
omp                  # запусти сессию, затем набери /login
```
Внутри сессии `/login` покажет список провайдеров. Отдельной CLI-команды `omp login` **не существует**;
если нужен именно терминал - `omp auth-broker login <провайдер>`.

**b) Через переменную окружения (ничего логинить не надо):**
```
export OPENROUTER_API_KEY=sk-or-...     # или OPENAI_API_KEY / DEEPSEEK_API_KEY / XAI_API_KEY / ...
```

Первый запуск нового пользователя: `omp setup` прогоняет мастер онбординга; внутри сессии `/login`
открывает тот же список провайдеров. Если ключей нет, omp честно скажет
`No credentials found ... use /login`. Если нет модели под ролью - `No models available`.

## 2. Распаковать архив

```
tar -xzf keel-harness-audited.tar.gz
cd keel-omp
```

## 3. Разложить файлы

Скриптом (безопасно: **существующий файл не перезаписывается молча** - скрипт его пропустит и
скажет «merge by hand»):

```
./install.sh          # macOS / Linux / Git Bash
./install.ps1         # Windows PowerShell
```

Или руками, если хочешь видеть каждый шаг:

```
mkdir -p ~/.omp/agent/agents ~/.omp/agent/extensions
cp agent/extensions/keel.ts   ~/.omp/agent/extensions/
cp agent/AGENTS.md            ~/.omp/agent/
cp agent/APPEND_SYSTEM.md     ~/.omp/agent/     # НОВЫЙ файл - без него оркестратор без механики
cp agent/RULES.md             ~/.omp/agent/
cp agent/agents/*.md          ~/.omp/agent/agents/
mkdir -p ~/.omp/agent/skills
cp -r agent/skills/*/          ~/.omp/agent/skills/   # ОДИН уровень: skills/<имя>/SKILL.md
cp agent/mcp.json             ~/.omp/agent/
cp agent/config.yml           ~/.omp/agent/
cp agent/models.yml           ~/.omp/agent/
```

> **Если у тебя УЖЕ есть `~/.omp/agent/config.yml`** (omp был настроен раньше), не перезаписывай его
> целиком - потеряешь свои личные настройки. Смотри раздел «Что в config.yml» ниже: вручную перенеси
> в свой файл только **харнесс-критичные** ключи. Личные настройки (тема, клавиши и т.п.) остаются
> твои. Второй вариант - ставить харнесс в project-scope (тоже ниже), тогда user-config вообще не
> трогается.

## 4. Вписать реальные модели

Открой `~/.omp/agent/config.yml`, в блоке `modelRoles` замени плейсхолдеры `KEEL_SETUP_REQUIRED`
на слаги своих моделей. Точные слаги - в `/models` внутри omp или у провайдера.

| Роль | Кто это в харнессе | Требование |
|---|---|---|
| `default` | оркестратор (primary) | быстрая; координирует и релеит больше всех |
| `plan` | планировщик | сильная, **строгосхемная** (план - фундамент) |
| `slow` | ревьюер | сильная, строгосхемная |
| `vision` | картинки/скриншоты | **обязана принимать изображения** |
| `designer` | UI-концепты | по вкусу |
| `smol` | скаут / дешёвый веер | дешёвая, быстрая |
| `tiny` | заголовки, память, фон | самая дешёвая |

Плюс в `~/.omp/agent/agents/coder.md` поле `model:` - модель кодера (тоже плейсхолдер).

**Кодер и ревьюер НЕ должны быть на модели, которая роняет строгие JSON-схемы** (у DeepSeek через
OpenRouter это наблюдается): done-отчёт кодера и вердикт ревьюера ходят строгой схемой, и при сбое
схемы верификация молча перестанет работать. Ставь туда строгосхемную модель.

## 5. Проверить установку

```
./verify.sh           # или ./verify.ps1
```

Должно быть **0 failed**. Если видишь `NO placeholder model ids left - FAIL` - шаг 4 не доделан
(остался хотя бы один `KEEL_SETUP_REQUIRED`).

## 6. Живая проверка

Запусти `omp` в любой папке. Внизу должна появиться строка:

```
KEEL свободный режим   ✓ коммит 12м назад
```

### Как читать статус-строку

Она собрана из сегментов; лишнее само исчезает.

**Шаг** — где мы в пайплайне (`приём → план → гейт → работа и приёмка`):

| Строка | Что значит |
|---|---|
| `KEEL свободный режим` | задача не начата: нет `docs/`. Чтение, вопросы и разведка свободны; кодер без контракта не запустится |
| `KEEL 1/4 · собираем задачу` | контракта ещё нет |
| `KEEL 1/4 · в контракте пустые места` | остались `<...>` — кодер и ревьюер не запустятся |
| `KEEL 2/4 · планирование` | контракт готов, нужен план от планировщика |
| `KEEL 3/4 · проверка плана` | план есть, его смотрит ревьюер |
| `KEEL 4/4 · впиши название задачи в реестр` | план одобрен, но строка задачи в `docs/report.md` осталась заглушкой |
| `KEEL 4/4 · работа и приёмка · открыто 2` | идёт работа, 2 пункта приёмки не закрыты |
| `KEEL 4/4 · приёмка закрыта — закрой задачу` | всё проверено: коммить и отметь задачу в реестре |
| `KEEL документы от прошлой задачи` | контракт/план остались от прошлой, новых задач нет |

**Кто работает** — `⟳ coder`, `⟳ planner`, пока субагент реально бежит.

**Git** — в безопасности ли работа: `✓ коммит 12м назад` · `● 3 файла не сохранено · коммит 2ч назад` ·
`⚠ приёмка закрыта, но 8 файлов не сохранено — закоммить`. Не git-репозиторий → сегмента нет.

**Алерты** появляются, только когда нужен ты: `⚠ впиши модели в config.yml`,
`⚠ застряли на «out-of-scope» — скажи, что менять`.

**Нет строки = расширение не загрузилось, и ни один гард не работает.** Тогда проверь, что omp видит
расширение:

```
omp -p '/extensions'
```

Если keel там не появился, положи файл вторым допустимым путём:

```
mkdir -p ~/.omp/agent/hooks/pre
cp agent/extensions/keel.ts ~/.omp/agent/hooks/pre/keel.ts
```

При самом первом запуске после установки, пока в `config.yml` остаются плейсхолдеры, KEEL один раз
подскажет прямо в сессии, что нужно вписать модели.

## Что в config.yml - и чей он

`config.yml` - **кастомный для харнесса**, он влияет на работу пайплайна. Его ключи делятся на два
класса:

**Харнесс-критичные (менять нельзя - на них держатся гарды и пайплайн):**
- `tools.approvalMode: yolo` - гейты делает keel.ts (BLOCK'и), а не диалоги одобрения omp.
- `task.*` (isolation, enableLsp) - как спавнятся субагенты.
- `memory.backend: mnemopi`, `compaction.enabled`, `inspect_image.mode`, `defaultThinkingLevel`.
- `bash.patterns` - жёсткая защита от разрушительных команд (под yolo `deny`/`prompt` всё равно
  действуют; правила проверяются по порядку, первое совпадение выигрывает).

**Личные (твои):**
- `modelRoles` - какие модели за какими ролями. Это ты подставляешь под свои креды.

Порядок применения в omp: `defaults <- user (~/.omp/agent) <- project (<cwd>/.omp) <- overlay`.
Настройки **сливаются по ключам** (deep-merge), а project-конфиг переопределяет user. Поэтому:

- **User-scope** (по умолчанию, `~/.omp/agent/`): харнесс работает во всех проектах. Минус - надо
  аккуратно слить `config.yml` с уже существующим.
- **Project-scope**: положи `agent/*` в `<твой-проект>/.omp/` вместо `~/.omp/agent/`. Тогда user-
  конфиг не трогается вообще, харнесс включается только в этой папке, а его model-роли для проекта
  авторитетны. Удобно, если не хочешь менять глобальную настройку.

## Скилы

Дисциплина агентов лежит в `~/.omp/agent/skills/<имя>/SKILL.md` - **ровно один уровень**, вложенные
группы omp не находит. Восемь скилов ставятся вместе с харнессом; какие кому достаются, описано в
`MANIFEST.md`.

Важное свойство: если файл скила не доехал, **omp молча его игнорирует** - без ошибки и без
предупреждения, агент просто останется без своей дисциплины. Поэтому `verify.sh` отдельно проверяет,
что каждое имя из `autoloadSkills` каждого агента имеет реальный файл на диске. Если увидишь
`[FAIL] autoloadSkills all exist` - скилы не скопировались.

Свои скилы можно добавлять рядом: положи `~/.omp/agent/skills/<твоё-имя>/SKILL.md` и впиши имя в
`autoloadSkills` нужного агента (или оставь без вписывания - тогда агент подтянет его по требованию
через `skill://<имя>`, потому что имя и описание всех скилов и так видны в промпте).

## Изоляция от Claude Code и других агентов

Если у тебя стоят Claude Code, Codex, Gemini CLI, opencode или Copilot, omp **по умолчанию читает
их конфиги** и подмешивает найденное: контекст-файлы, MCP-серверы, слэш-команды, скилы, хуки, тулы и
настройки. При нескольких установленных инструментах в сессию приезжает много чужих инструкций,
которых ты не заказывал.

В `config.yml` харнесса уже стоит:

```yaml
disabledProviders: [claude, codex, gemini, opencode, github]
```

Это убирает **весь** источник целиком, а не только его контекст-файл.

Что при этом **не** ломается: наши файлы принадлежат провайдеру `native` (`~/.omp/agent/...`), он не
отключается. Более того, скилы `native` имеют приоритет **100** — выше claude (80), codex (70) и
opencode (55). Дедуп идёт по имени скила, побеждает первый по приоритету, так что наш `karpathy`
выигрывает у любого одноимённого из Claude Code даже без отключения.

Намеренно оставлены включёнными `agents` (`~/.agent`, `~/.agents`) и `agents-md` (обычный
`AGENTS.md` в репозитории) — это нейтральное соглашение, а не конфиг чужого инструмента, и файл
проекта обычно стоит читать. Добавь их в список, если хочешь, чтобы харнесс игнорировал и это.

## Advisor (WATCHDOG) — нам не нужен

omp умеет подключать к сессии модель-советчика: она читает транскрипт, ходит по файлам своими
инструментами и подкидывает замечания. Выключен по умолчанию (`advisor.enabled: false`), и включать
его не стоит:

- это **отдельная модель, работающая параллельно на каждом обновлении транскрипта** — прямое
  удвоение расхода, а при `task.agentAdvisor` ещё и на субагентах;
- его роль у нас уже занята — ревьюер, только тот стоит в пайплайне механически, а советчик
  говорит в сторону;
- через `WATCHDOG.yml` ему можно выдать `edit`, `write`, `bash`. Его вызовы проходят через гарды
  KEEL (проверено: обёртка эмитит `tool_call` до исполнения), но он работает в отдельной сессии без
  контракта и фазы, так что из защит на него ложится только scope-lock.

Если всё же включишь — не давай ему меняющих инструментов; штатный набор `read`/`grep`/`glob`
безопасен.

## Linux, macOS, Windows - поведение одинаковое

Харнесс не делает различий между платформами, и это проверено:

- **Шелл.** omp сам выбирает шелл: Git Bash на Windows, `$SHELL` на Linux/macOS, `cmd.exe` только если
  bash в системе нет. Настройка `shellPath` позволяет указать свой (например PowerShell). KEEL
  распознаёт запись во всех трёх синтаксисах - POSIX (`>`, `cp`, `tee`, `sed -i`), PowerShell
  (`Set-Content`, `Out-File`, `Copy-Item`, `Remove-Item`, ...) и cmd (`copy`, `move`, `del`, ...),
  так что код-фенс работает одинаково при любом шелле.
- **Пути.** Разделители нормализуются с обеих сторон: SCOPE, записанный как `src\file.ts`, совпадает
  с вызовом `src/file.ts` и наоборот. Пробелы и кириллица в путях поддерживаются.
- **Переводы строк.** Файлы с CRLF (`docs/plan.md`, `docs/report.md`) читаются так же, как с LF.
- **Определение «отревьюен ли план»** сделано по отпечатку содержимого, а не по времени файла -
  на FAT/exFAT разрешение времени 2 секунды, и сравнение по времени там было бы ненадёжным.
- **Сравнение путей регистронезависимое на всех платформах.** Linux различает регистр, но KEEL
  намеренно ведёт себя одинаково везде: `SRC/A.ts` и `src/a.ts` считаются одним и тем же. Так
  поведение переносимо между машинами; цена - крайне редкий случай, когда на Linux два файла
  различаются только регистром.
- **Установщики и верификаторы** идут парами (`install.sh`/`install.ps1`, `verify.sh`/`verify.ps1`)
  и проверяют одно и то же; набор проверок в них совпадает.

Единственное, что действительно зависит от платформы, - это внешние программы (git, Node, языковые
серверы). Их ставишь как обычно для своей ОС.

## Языковые серверы (позже, когда дойдёшь до реального проекта)

Нужны для кросс-файловых проверок (LSP). Ставятся по одному на язык проекта, все через Node -
поэтому Node первым:

- Python -> `pyright`
- TypeScript -> `tsserver`
- Vue -> `@vue/language-server`

Без сервера проверки для этого языка тихо падают на grep и теряют точность. KEEL при этом блокирует
запись через lsp (rename/code-actions) - lsp остаётся только на чтение (definition/references/hover/
diagnostics), а любые правки идут через кодера с edit/write.

## Браузер для живой проверки UI

В `~/.omp/agent/mcp.json` прописан MCP-сервер браузера. Нужен, чтобы кодер доказывал работу
интерфейса реальным снимком страницы, а не чтением исходников. Если сервер не ставится - это не
блокирует харнесс, просто UI-проверки будут слабее.

## Что важно знать сразу

**В папке без `docs/` свободны чтение, вопросы и разведка** — но не работа: кодер и ревьюер без
контракта и SCOPE не запустятся нигде, даже в чистой папке. Можешь спокойно щупать систему, задавать
вопросы, править файлы. Ограничения (scope-lock, code-fence и прочее) включаются только там, где
есть `docs/` с планом - то есть в настоящей работе над проектом.

Как этим пользоваться дальше - в `USAGE.md`. Что где лежит и почему - в `MANIFEST.md`.
