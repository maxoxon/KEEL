## Субагенты -> `~/.omp/agent/agents/` (реальный frontmatter)
| Файл | model | tools (allowlist) | read-only? | blocking | spawns | output |
|---|---|---|---|---|---|---|
| `planner.md` | `@plan` | read, grep, glob, lsp | нет (lsp*) | **да** | scout | plan + contract |
| `reviewer.md` | `@slow` | read, grep, glob, lsp, ast_grep, inspect_image | нет (lsp*) | **да** | scout | verdict + next_prompt |
| `coder.md` | (placeholder) | read, edit, write, bash, grep, glob, lsp, **debug**, inspect_image | нет (пишет) | - | scout | contract_met/evidence/did_not_verify/remaining |
| `designer.md` | `@designer` | read, grep, glob, inspect_image | **да** | - | - | concept |
| `scout.md` | `@smol` | read, grep, glob | **да** | - | - | summary + locations |

omp дополняет эти списки сам: `ast_edit` - всем, у кого есть `edit`; `ast_grep` - всем, у кого есть
`grep` (мы включили `astGrep.enabled`); `recall`/`retain`/`reflect`/`memory_edit` - всем, потому что
`memory.backend: mnemopi`. То есть фактический набор шире объявленного; на классификацию read-only
это не влияет (все добавки в read-множестве omp), а `ast_edit` покрыт нашим MUTATING.

Read-only = сам список `tools:` (все тулзы в read-множестве omp). **Никакого `restrictToolNames`/
`mode` в агент-файле - таких ключей в omp нет.** (*) planner/reviewer держат `lsp` для навигации
(read); его write-действия рубит GUARD 11. blocking:true у planner/reviewer = «родитель ждёт вердикт
инлайн», без него relay ловить нечего. spawns: scout = omp сам показывает субагенту только scout.

autoloadSkills: у coder/reviewer/designer - закомментированная подсказка (скилы по профилю).
planner/scout - без неё. Скилы лежат в `~/.omp/agent/skills/<имя>/SKILL.md`, неизвестные имена omp
игнорирует. Метаданные всех скилов и так видны всем агентам; тело тянется через `read skill://`.

## Скилы -> `~/.omp/agent/skills/<имя>/SKILL.md`
Ровно один уровень вложенности - omp не находит группы вида `skills/группа/скил/`.

| Скил | Кому и как | Что даёт |
|---|---|---|
| `karpathy` | coder, автоинжект | думать до кода, простота, хирургические правки, проверяемый критерий |
| `surgical-coding` | coder, автоинжект | наименьшее корректное изменение, без AI-отпечатка |
| `ponytail` | coder, planner, reviewer, автоинжект | лестница лени: не строить, если можно не строить (MIT, автор Dietrich Gebert) |
| `worktree-freshness` | scout, coder, reviewer, автоинжект | не делать структурных выводов из устаревшего worktree |
| `decision-guard` | planner, reviewer, автоинжект | решения по доказательствам, а не по правдоподобию |
| `agent-brief` | reviewer, автоинжект | 3 C's: Context/Constraints/Composition, intern-test, «don't finish until» |
| `visual-tooling` | coder, reviewer - **ситуативно** | процедура QA через браузер; впрыскивается keel, когда в контракте заполнен Frontend |
| `project-state` | оркестратор - через `APPEND_SYSTEM.md` | карта путей документов, компакция по классам, параллельные сессии |

Автоинжект = `autoloadSkills` во frontmatter агента: omp вливает **полное тело скила до первого
промпта**, модель не может забыть его прочитать. У оркестратора автозагрузки нет вовсе (это
primary-сессия, а не агент), поэтому его содержимое живёт в `APPEND_SYSTEM.md`.
**omp молча игнорирует несуществующее имя скила**, поэтому `verify.sh` проверяет, что каждое имя из
`autoloadSkills` имеет реальный `SKILL.md` на диске.

## Расширение -> `~/.omp/agent/extensions/keel.ts`
**11 механических гардов** (все fail-open на баге хука - баг не морозит сессию):
1. **план-гейт** - `ui.confirm` перед стартом кодера (единственный, кто спрашивает);
2. **код-фенс** - primary пишет только 4 control-файла (`docs/contract.md/plan.md/report.md/review.md`), всё прочее блок - через edit/write/ast_edit И через shell-редирект;
3. **чекпоинт** `refs/keel/checkpoint` перед первой правкой сессии (git stash create, дерево не трогает);
4. громкая пометка провалившегося вызова (`tool_result.isError`);
5. пометка «exit 0 без вывода» (пустой артефакт);
6. **контракт системно обязателен** - `coder`/`reviewer` не спавнятся без `docs/contract.md` и с незакрытыми переменными (`<...>`/TBD); текст контракта впрыскивается им в промпт (batch-shape task);
7. **scope-lock** - меняющая операция (edit/write, shell-запись, MCP-акторы/ассеты, lsp-write) вне `<!-- SCOPE -->` из `docs/plan.md` блокируется; без usable-scope в harness-проекте fail-closed;
8. **дословный релей ревью** - `next_prompt` ревьюера читается из `structuredOutput.data` и доходит до кодера через расширение, а не пересказом оркестратора;
9. **топология спавнов** - только primary запускает ролевого агента; субагент зовёт лишь read-only scout (рекурсия и кросс-запись исключены; подпёрто нативным фильтром ростера omp);
10. **session_stop** - не даёт сдать работу с незакрытым чек-листом приёмки (пушбек, max 2; хук не срабатывает для субагентов, капается на 8);
11. **lsp write-actions** - rename/rename_file/code_actions(apply) блокируются (кодер пишет через edit/write); lsp-чтение (definition/references/hover/diagnostics/symbols) остаётся;
12. **один писатель за раз** - в одном вызове нельзя запустить двух кодеров, нельзя кодера рядом с ревьюером (это последовательные стадии), нельзя второго кодера, пока работает первый. Чтения (скауты) веером - свободно;
16. **живой харнесс не редактируется из сессии** - никто не переписывает `keel.ts`, свой агент-файл, `RULES.md` или `config.yml`. Гард, который может удалить тот, кого он ограничивает, не гард. Правка харнесса - из терминала либо как обычный проект со своим контрактом и SCOPE;
15. **субагент не пишет контрольные файлы** - контракт, план со SCOPE, реестр и вердикт принадлежат оркестратору. Кодер, способный править `docs/plan.md`, расширил бы себе scope; способный править `docs/review.md` - подделал бы вердикт, которому обязан подчиняться. Своё субагент пишет в `docs/PHASE_REPORT_<слаг>.md`;
14. **тип задачи — механика**: строка `Тип:` в `docs/contract.md` обязана распознаваться; она задаёт правила, впрыскиваемые в каждый спавн, уровень `effort` и (для `audit`) отказ кодеру;
13. **read-only агенты ничего не меняют** - scout/designer/planner блокируются на любом инструменте, который не опознан как чтение. Это единственное покрытие для MCP: список `tools:` фильтрует только встроенные тулы, а MCP-инструменты доходят до субагента независимо от того, что написано в его файле.

Плюс: первый запуск (пока в config плейсхолдеры) один раз подсказывает вписать модели
(`sendMessage` deliverAs:nextTurn); сегментная статус-строка (фаза · алерт · кто работает · git); каждый ход
primary в контекст впрыскивается текущая фаза (выведена из состояния `docs/` на диске).

## Типы задач -> строка `Тип:` в `docs/contract.md`

Перенос слэш-команд Claude Code. Там тип жил в том, какую команду ты набрал - его можно было забыть,
и ничто его не принуждало. Здесь он лежит на диске, переживает `/clear` и рестарт, виден в
статус-строке и меняет **механику**, а не формулировки.

| Тип | Гейтов | effort | Что меняет |
|---|---|---|---|
| `bug-fix` | 1 | hi | корневая причина устанавливается ОТЛАДЧИКОМ, не рассуждением; наименьшая безопасная правка |
| `small-feature` | 1 | med | расширять существующее, наименьший безопасный вариант |
| `large-feature` | 3 | hi | по милям, после каждой - сквозная проверка импортов |
| `refactor` | 1 | hi | поведение идентично; проверки ДО и ПОСЛЕ как доказательство |
| `architecture-change` | 3 | hi | обоснование изменения, точки отката, совместимость между стадиями |
| `new-project` | 3 | med | первая миля = MVP, наименьшие самостоятельно проверяемые мили |
| `audit` | 1 | hi | **кодер не запускается вовсе**; непересекающиеся зоны скаутам; покрытие проверяется числом |
| `adopt` | 1 | med | описать существующее по файловой системе, ничего не переписывая |

Нераспознанный или отсутствующий тип **блокирует** спавн кодера и ревьюера с перечнем валидных: без
этого опечатка молча отключала бы всю механику типов. Регистр и пробелы не важны, `Type:` тоже
читается, заглушка шаблона типом не считается.

## Поведение платформы, на которое опирается харнесс (проверено по исходнику omp)

- **`tool_call` fail-closed.** Если обработчик расширения упал или превысил бюджет (30 с,
  `extensionHandlers.toolCallTimeoutMs`), omp **блокирует** вызов: «неотвечающее расширение не
  считается молчаливым согласием». Внутренние try/catch keel ловят свои баги и пропускают вызов -
  платформа строже, и это правильный порядок.
- **Диалог не съедает бюджет.** `ui.confirm` ставит таймер обработчика на паузу и возобновляет
  после ответа, поэтому гейт плана может ждать человека сколько угодно.
- **Первый блок побеждает.** При нескольких расширениях omp возвращает первый `block` и
  останавливается. Но не-блокирующий результат (наш впрыск контракта через `{input}`) может быть
  перезаписан другим расширением, которое тоже переписывает `input`. Если поставишь такое - проверь
  порядок загрузки.
- **Сбой загрузки расширения не останавливает omp.** Ошибка попадает в `LoadHooksResult.errors`, и
  загрузка продолжается. Единственный видимый признак - **пропавшая статус-строка KEEL**. Увидел,
  что её нет, - гарды не работают, см. `INSTALL.md`.

## Ключевой принцип размещения
- **Механика** (нельзя обойти): `tools:` allowlist (read-only), `output:`-схема (done-report),
  approvalMode yolo + bash.patterns, blocking:true, extension (17 гардов).
- **Дисциплина**: тела агентов (самодостаточны) + AGENTS.md + APPEND_SYSTEM.md + RULES.md.
- **Рабочее состояние**: `docs/`-файлы (переживают компакцию). **Долгая память**: нативная mnemopi.
